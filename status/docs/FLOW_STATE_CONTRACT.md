# 各项目怎么把「这一步跑完了」告诉 status

## 一句话

在你的仓里放一份 `docs/governance/flow_state.json`，**由你自己的 CI 或 cron 写**，
每次那一步真的跑完就更新它。status 每小时来读一次，只读不写。

## 为什么必须有这个

status 现在的自动核查全是**主机侧**的：看进程在不在、容器活没活、文件新不新、库里有几行。

实测线上 49 个在跑的程序，逐个对下来：

| 系统 | 主机上属于它的程序 |
|---|---|
| Alpha | 13 |
| Status | 5 |
| KMFA / EEI | 各 3 |
| PFI / Serenity | 各 2 |
| **KM_IDSystem** | **0** |
| **whkmSalary** | **0** |
| **arxiv-daily-push** | **0** |

后三个合计 70 个步骤 = 全部 253 步的 28%。**主机侧核查对它们永远探不到**——
不是没配，是没有可核查的对象。所以：

> 就算其余系统每一步都装上自动核查，覆盖率天花板也只有 **72%**。
> owner 定的 **85%** 用现有那套在数学上够不到。

这份文件是唯一的解法，也是「双向」里回流的那一半：
本站 → 各条线（看板）；各条线 → 本站（自己吐状态）。

## 格式

```json
{
  "schema": "linze.flow_state.v1",
  "steps": {
    "BL-OPME-KILN.intake": {
      "state": "healthy",
      "at": "2026-07-27T08:00:00+08:00",
      "n": 128,
      "note": "本轮接入 128 条工单"
    }
  }
}
```

- **键** = `<baseline id>.<stage>`，和你 `flow.yaml` 里的写法一致。
  只允许 `A-Za-z0-9_.:-`，最长 80 字符。
- **state** 只能是这七个之一：
  `healthy` / `degraded` / `blocked` / `blocked_by_input` /
  `blocked_by_policy` / `not_built` / `unknown`。
  **写别的词会被直接丢掉**，不会被猜成通过。
- **at** 必须带时区偏移（`+08:00` 这样）。没有偏移的按北京时间算。
- **n**（可选）本轮产出了多少条，整数。
- **note**（可选）一句话，超过 120 字会被截断。

然后在 `flow.yaml` 对应格子里挂上：

```yaml
      intake:
        state: healthy
        probe: repo_state
        args: {key: "BL-OPME-KILN.intake", max_age_h: 26}
        evidence: 由本项目 CI 在每轮接入完成后写入 flow_state.json
```

## 三条不会让步的规矩

1. **过期一律降级成「不确定」。** 超过 `max_age_h`（默认 26 小时）的记录，
   既不算通过、也不算断了。三个月前跑通过不等于今天跑通了。
2. **报忧和报喜一样重要。** 你自己写 `blocked_by_input` 就会照实显示成
   「断了（等你给材料）」并进 owner 的待办表。这个通道不是用来刷绿的。
3. **绝不能拿相邻信号冒充这一步的产出。** 「容器还活着」不等于
   「结算数据导出了」。用前者充当后者，覆盖率会瞬间冲到 90% 而且**永远是绿的**——
   这正是这个项目反复栽过的假绿。**宁可覆盖率难看，不要假覆盖。**

## 这份文件不是指令，是数据

status 只从里面取三样东西：认得出的状态词、能解析的时间戳、截断后的一句话。
路径、命令、表达式一概不读。解析失败如实留原因，不会当成通过。
